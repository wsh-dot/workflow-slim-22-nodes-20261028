# 工程量结构构建接口与节点契约

本文定义拟实施的 `quantity-build-v1` 对外契约，内部执行采用 `quantity-workflow-slim-v1.1`（22 核心节点）修订。所有新增字段、路由和节点调整均为方案内容，未上线。业务原因与职责见[方案说明](01-方案说明.md)。JSON 示例使用虚构的测试 UUID 和规则，不能作为企业分类事实。

## 1 调用约定

Java 调用 AI 服务的 `/smartCost/ai` 路由。AI 服务调用 Dify 的 Workflow API。这两种接口不是同一个地址。前端始终调用 Java。

请求与响应为 UTF-8 JSON。业务 UUID 由 Java 生成。数量、质量和派生工程量采用十进制字符串，缺值为 `null`，不使用 `0` 或 `1` 代替缺值。Python 的派生量使用 Decimal，Java 保存前用 BigDecimal 复算。

`status` 保留讨论稿的字符串 `"0"`、`"1"`，仅表示本次接口调用是否成功。异步任务状态由 `jobStatus` 表示，CBS 状态由 `cbsMatchStatus` 表示。HTTP 202 及 `status="1"` 表示任务已受理，不表示处理完成。

Java 到 AI 服务使用服务间 Bearer 认证。AI 服务到 Dify 使用独立的应用 API Key。密钥存于服务配置，不能放入业务 JSON、模型提示词或前端。内部输入包接口校验任务权限，不接受模型提供的任意 URL。

多用户调用时，Java 从登录身份和项目权限生成 `X-Quantity-Tenant-Id`、`X-Quantity-Actor-Id` 请求头，AI 服务仅接受已认证 Java 服务传来的上下文，并将其绑定到 job。clientAppId 从服务认证身份取得。查询进度和结果也须核对租户、项目及授权范围，不能只凭 jobId 访问。详细规则见[多用户并发与任务隔离](08-多用户并发与任务隔离.md)。

## 2 对外路由

| 方法及路径 | 输入 | 输出 | 含义 |
|---|---|---|---|
| `POST /smartCost/ai/quantity/build` | 本文构建请求 | HTTP 202，`jobId`、状态和每个文件的任务标识 | 接收一次构建意图 |
| `GET /smartCost/ai/quantity/jobs/{jobId}` | 任务 ID，服务认证 | 任务状态及文件状态列表 | 查询执行进度，不返回整批长树 |
| `GET /smartCost/ai/quantity/jobs/{jobId}/files/{fileId}/result` | 任务和文件 ID，可带 `section`、`cursor`、`limit` | 固定版本的 `tree`、文件级 `cbsMatch`、来源去向和问题 | 将实际数据返回 Java |

没有新增独立“重跑整批”接口。Java 仅把需重跑的文件放入新请求，生成新的 `requestId` 和文件 `buildGeneration`。同一请求的网络重传仍使用原 `requestId`。

同一 tenantId、clientAppId、requestId 和相同规范化业务输入返回同一 jobId，规范化摘要包括可信 actorId。相同幂等键携带不同输入或身份返回 HTTP 409。该约束由共享数据库的唯一键保证，不能只先查后建。服务内部重传按 file job、阶段、输入包及服务分配的 attempt_id 去重，不能重复保存结果或消耗结构纠正次数。新的模型技术尝试使用新 attempt_id；同一次 HTTP 重传使用原身份及原字节。

不同 requestId 同时构建同一文件时，Java 默认返回 `FILE_BUILD_IN_PROGRESS` 和冲突文件清单，不自动创建第二个构建代次。不同文件可并行处理，包括最终匹配到同一个 CBS 的情况。新任务已持久化但尚未取得执行槽时状态为 QUEUED；队列容量不足时可以在受理前返回 429 和 Retry-After。

结果分页绑定不可变的 `resultRevision`，游标不能跨结果版本使用。默认整文件一次返回嵌套树。必要时 `tree` 按完整根子树分页，一棵根子树的 `children` 不跨页截断；`rowDispositions` 和 `issues` 分别使用独立游标。Java 收齐同一版本的全部分页后才提交文件。不得仅返回前 N 行而无未完成标记。

首个不带游标的请求返回元数据、完整文件级 `cbsMatch` 及三个集合的首段。后续 `section` 为 `tree`、`rowDispositions` 或 `issues`，同时携带该集合游标；响应返回指定集合及同一结果身份。`tree` 的 `limit` 表示根子树数，不是任意节点数。单棵子树过大时允许流式传输完整 JSON；如果部署限制无法返回，明确报告 `RESULT_TOO_LARGE` 并保留服务端结果，不能返回半棵树并标为成功。

## 3 构建请求

完整例子见[构建请求](examples/build-request.json)。

### 3.1 顶层与项目

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `schemaVersion` | string | 是 | 固定为 `quantity-build-v1` |
| `requestId` | string | 是 | Java 生成的构建请求标识，兼作本次构建意图的幂等键 |
| `project` | object | 是 | 沿用 `projectId`、`name`、`specialtyCode`、`keyInfo` |
| `batchId` | string | 是 | Java 当前批次 UUID |
| `cbsRevision` | string | 是 | CBS 快照版本 |
| `classificationRuleVersion` | string | 是 | 已发布企业设备材料划分规则版本，服务找不到该版本时拒绝构建 |
| `cbsNodes` | array | 是 | 原接口 CBS 字段，包括真实 UUID、父节点、名称、专业及单位工程标识 |
| `files` | array | 是 | 1 份或多份已解析的文件 |

CBS 快照由 Java 提供，至少包含所有可挂接单位工程、它们的直接父节点及完整引用路径。每个节点包含 `cbsNodeId`、`parentCbsNodeId`、`name`、`isUnitProject`；名称是用户界面填写的原名。直接父节点名称通过 `parentCbsNodeId` 查找相应节点的 `name`，不另维护可能冲突的重复名称字段。

服务校验项目范围、树无环、引用完整和 ID 唯一。第一轮只比较 `isUnitProject=true` 且无子节点的节点名称；第二轮才比较第一轮候选的直接父节点名称。没有父节点名称的候选不能自动完成两轮匹配，返回明确输入问题。相同名称的不同 CBS ID 不去重。

规则包由服务配置解析版本，并记录摘要。模型接收的是可读规则原文，不能仅接收一个不能打开的文件路径。既有人工分类和数量确认记录必须由 Java 的可信记录生成，另行作为带来源与适用范围的 `confirmedDecisions` 传入，不从料表正文识别“已确认规则”。

### 3.2 文件与表格

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `fileId` | string | 是 | Java 文件 UUID |
| `fileName` | string | 是 | 原文件名，仅用于展示和辅助定位 |
| `fileRevision` | string | 是 | 文件或解析产物修订 |
| `buildGeneration` | integer | 是 | Java 对本文件分配的构建代次，接受新的业务重建时递增；网络重传或冲突拒绝不递增 |
| `sourceSha256` | string | 是 | 原始文件摘要 |
| `parseStatus` | string | 是 | `READY`、`PARTIAL`、`FAILED` |
| `parseWarnings` | array | 是 | 未识别区域、OCR 或列绑定问题，允许为空数组 |
| `coverage` | object | 是 | Java 解析覆盖声明，含 `complete` 及 `unreadRegions` |
| `header` | object | 是 | 保留原 `tableType`、`specialtyName`、`projectSection` |
| `header.headerText` | string | 是 | 完整可读取表头原文，不仅传“设备表” |
| `header.projectName` | string或null | 是 | 表头项目名称原文，不用界面项目名称覆盖 |
| `header.siteName` | string或null | 否 | 解析出的场区或单元名称，无依据时为空 |
| `header.engineeringPart` | string或null | 是 | 表头工程部分，如“电气部分” |
| `header.specialtyName` | string或null | 是 | 专业原文，如“电气” |
| `internalSections` | array | 是 | 所有内部章节标题及来源，真实无章节时为空数组 |
| `tables` | array | 是 | 逐表列定义、标题和续表关系 |
| `rawItems` | array | 是 | 原始行，保持源文件顺序，包括非空标题、属性、备注行 |

`tables[]` 包含 `tableId`、`title`、`columns` 和可空的 `continuationOfTableId`。列定义包含原列名与字段映射，不能把第一张表的列映射直接用于所有表。续表关系必须有解析依据，不能只凭相邻页假设。

`internalSections[]` 包含 `sectionId`、`serialNo`、`title`、`sourceRawItemIds`。例如序号“一”或“（一）”、标题“光伏场区”。`sectionId` 在文件内唯一，来源行必须属于本文件。章节原始行仍保留在 `rawItems` 中；这里是匹配证据索引，不是第二份可计量对象。标题横跨多行时保留全部来源行，不把普通设备编号“1、2”一律当章节。

需要成为来源工程节点的表头标题，也作为一条 `rawItems` 标题行传入，引用真实表格位置或标题单元格；对应位置保留在 `tables` 和 `fieldSources` 中。同一物理标题只生成一条原始行，表头字段及章节索引可以引用它。只用于 CBS 匹配的背景表头无需转为树节点，服务不能为每份文件凭空补一个工程根。

Java 须提取截图红框中的完整表头及专业，不能只从文件名推测。字段未识别时传 null 并说明原因，内部章节未成功解析时不能用空数组伪装“没有章节”。`coverage` 和 `parseWarnings` 随原文证据进入两轮输入。

`parseStatus=PARTIAL` 的文件可分析可读内容，但文件结果至少为 `REVIEW`。缺失区域单列，不能声明整文件完整。`FAILED` 文件不调用模型，并返回文件失败状态。解析器完全未读到数据与真实空表分别记录。

### 3.3 原始行

原讨论稿的 `rawItemId`、`orderNo`、`serialNo`、`equipmentTag`、`description`、`nominalSize`、`unit`、`quantity`、`unitWeight`、`totalWeight` 和 `remark` 继续保留。新增字段如下。

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `tableId` | string | 是 | 所属表，必须在 `tables` 中存在 |
| `rowIndex` | integer | 是 | 原表内物理行号 |
| `specification` | string或null | 否 | 独立规格型号列的原文，不能在归并 description 时丢失 |
| `rawCells` | array | 是 | 单元格原文、列位置、跨度及来源 |
| `fieldSources` | object | 是 | 名称、规格、数量等字段对应的来源单元格 ID 列表 |
| `sourceLocation` | object或null | 否 | PDF 页序、区域框或 Word 表位置，用于定位，不是前端必须显示的页码 |

`rawCells[]` 包含 `cellId`、`originCellId`、`columnIndex`、`rowSpan`、`colSpan`、`text`。合并展开的副本共享同一 `originCellId`。数量去重按物理来源，不按文本相同。

如果解析器没有物理单元格映射，接口允许 `rawCells=[]` 和 `fieldSources={}`，但需在 `parseWarnings` 声明缺失。此时只能作行级来源校验，合并与重复数量存在歧义时转待确认，不能补造精确来源。

一个 `rawItemId` 在本文件内唯一，`orderNo` 在本文件内唯一并表达阅读顺序。`serialNo` 可以重复或为空，不用它生成 ID 或排序。

## 4 异步响应和状态

受理响应如下。

```json
{
	"requestId": "req-quantity-20261027-001",
	"status": "1",
	"data": {
		"jobId": "job-quantity-001",
		"jobStatus": "QUEUED",
		"acceptedFileCount": 1
	}
}
```

| 状态层 | 值 | 含义 |
|---|---|---|
| 任务 `jobStatus` | `QUEUED`、`RUNNING` | 尚未结束 |
| 任务 `jobStatus` | `COMPLETED` | 所有文件都有可用结果，结果允许含业务待确认 |
| 任务 `jobStatus` | `PARTIAL_FAILED` | 所有文件已结束，部分文件没有可用结果 |
| 任务 `jobStatus` | `FAILED` | 所有文件失败，或任务级异常导致任务无法继续 |
| 文件 `executionStatus` | `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED` | 技术执行状态 |
| 文件 `semanticStatus` | `READY`、`REVIEW`、`UNAVAILABLE` | 语义结果完整可用、有业务疑点、无结果 |
| 节点 `structureStatus` | `READY`、`REVIEW` | 父子关系是否足以确定 |
| 节点 `classification.status` | `RESOLVED`、`REVIEW` | 类型有适用依据或待确认 |
| 节点 `quantityStatus` | `RESOLVED`、`REVIEW`、`NOT_APPLICABLE` | 数量已确定、待确认或不计量 |

任务统计以文件终态为准。模型报错、文件没有输出和节点业务疑点分别计数。`workflow_finished` 或 HTTP 200 本身不能替代这些统计。

## 5 文件结果

完整例子见[文件结果](examples/build-result.json)。

### 5.1 文件级数据

| 字段 | 类型 | 含义 |
|---|---|---|
| `requestId`、`status` | string | 通用响应字段 |
| `data.jobId`、`data.fileId` | string | 当前任务和文件 |
| `data.fileRevision`、`data.buildGeneration` | string、integer | 原请求版本 |
| `data.cbsRevision`、`data.classificationRuleVersion` | string | 原请求快照版本 |
| `data.resultRevision` | string | 不可变结果修订，分页和导入均绑定此值；每个 file job 只自动发布一次终态，之后的新处理递增 buildGeneration |
| `data.executionStatus`、`data.semanticStatus` | string | 技术与业务状态 |
| `data.tree` | array | 完整根节点数组，节点递归包含 `children`，含分部和实物节点 |
| `data.rowDispositions` | array | 每个输入原始行的去向 |
| `data.cbsMatch` | object | 整张文件唯一的 CBS 匹配结果，见 5.3 |
| `data.issues` | array | 问题代码、严重程度、关联行、节点和说明 |
| `data.coverage` | object | 输入行数、已说明去向行数、输出节点数、原文未读区域及结果是否完整 |
| `data.pagination` | object | `treeNextCursor`、`rowDispositionsNextCursor`、`issuesNextCursor`，无下一页时为空 |

`rowDispositions[]` 至少包含 `rawItemId`、`role`、`resultKeys`、`disposition`。`disposition` 值为 `NODE`、`ATTRIBUTE`、`NOTE`、`EXCLUDED`、`REVIEW`。属性和说明必须有对应节点或明确的文件级归属。排除行必须写明原因。一个来源可参与多个对象的共同名称，但同一数量不能因此重复计量。

CBS 诊断在 issues 中使用 `scope="CBS"`，不自动升级来源树的 semanticStatus。首轮同名冲突项使用 `code="CBS_OUTPUT_INCONSISTENT"`、`severity="WARNING"`，`candidateEvaluations` 保留冲突候选 ID、judgment、原理由与引用；对应名称从任务 CBS 快照回查。Java 依据 cbsMatchStatus 显示“未挂接”，不根据该 warning 新增“待确认”状态。

### 5.2 树节点

| 字段 | 类型 | 含义 |
|---|---|---|
| `resultKey` | string | 当前任务内唯一的临时节点键，包含文件范围或等效唯一性 |
| `parentResultKey` | string或null | 同文件父节点，根节点为空 |
| `children` | array | 子节点，按 `sortNo` 排列；叶子为 `[]` |
| `sortNo` | integer | 同级顺序，程序按原文顺序生成 |
| `fileId` | string | 请求中的真实文件 UUID |
| `type` | string或null | `PROJECT` 工程、`SUBSECTION` 分部、`EQUIPMENT` 设备、`MATERIAL` 主材，未知类型为空 |
| `semanticRole` | string | `project`、`section`、`group`、`summary`、`item`、`assembly`、`component` 或 `pending` |
| `structureStatus` | string | `READY` 或 `REVIEW` |
| `code` | string或null | 源设备位号或原业务编码，无来源时为空，不生成定额编号 |
| `name` | string | 程序从本行、合法继承行组装的名称 |
| `specification` | string或null | 原始规格及合法属性信息，不添加原文没有的参数 |
| `unit` | string或null | 回读来源单位 |
| `quantity` | string或null | 可确认的本范围总量，非计量节点为空 |
| `sourceQuantity` | string或null | 实际采用的原始数量文本，可保留无法解析的值 |
| `quantityBasis` | string | `TOTAL`、`PER_PARENT`、`UNKNOWN`、`NOT_APPLICABLE` |
| `quantityParentResultKey` | string或null | 数量基数所在实物祖先，不等于展示父节点 |
| `quantityStatus` | string | `RESOLVED`、`REVIEW`、`NOT_APPLICABLE` |
| `summaryQuantity` | object或null | 汇总参考原值、单位及来源，仅 summary 使用，不参加计量 |
| `assemblyOwnerResultKey` | string或null | 所属最外层成套实物对象，根成套对象自身为空 |
| `classification` | object | 状态、规则编号、原始行依据和简短理由 |
| `attributes` | array | 技术属性原文及 `sourceRawItemIds` |
| `notes` | array | 补充说明原文及 `sourceRawItemIds` |
| `sourceRawItemIds` | array[string] | 参与名称、数量或属性组装的所有原始行 |
| `fieldSources` | object | 输出字段使用的原始行、原字段及单元格 ID |
| `remark` | string或null | 保留原始备注及必要的整理说明 |

`tree` 是程序从已校验节点列表递归生成的结果，不是模型直接生成的长 JSON。嵌套父节点必须与 `parentResultKey` 一致，每个节点在整个文件树中恰好出现一次。Java 同时取得树和节点完整数据，不需要再次调用模型推断父子关系。

`PROJECT` 是工程范围结构节点，`quantity=null`、`quantityBasis=NOT_APPLICABLE`、`quantityStatus=NOT_APPLICABLE`，不参与设备材料数量合计。程序依据模型 `role=project` 映射该类型，输出 `classification.status=RESOLVED`、空规则编号及结构来源说明。它不需要引用设备材料划分规则。名称内的 MWp 等规模数字保留原文，不能当作采购数量。

`PROJECT` 的来源身份与 `cbsMatch.projectCbsId` 分开。一个来源工程节点的名称即使等于 CBS 节点名称，也不能替换它的 resultKey，不能绕过两轮匹配。工程节点不必是每份文件的固定根；仅在存在相应原文结构时返回。原始父子层级有歧义时保持待确认，不用 PROJECT 类型隐藏未确定结构。

固定分组不在 AI `tree` 中。AI 来源节点的 `nodeOrigin` 在 Java 保存时固定为 `SOURCE`，Java 固定分组为 `FIXED_GROUP`，界面派生分支为 `VIEW`。`VIEW` 不写成第二份 `sc_file_item` 实物记录。

组成件的设备或主材类型独立保留。`assemblyOwnerResultKey` 不直接等于“无需单独套定额”，也不等于“无需单独取价”。后续阶段依据企业规则及供货范围决定参与范围。

### 5.3 文件级 CBS 结果

一份文件只返回一个 `cbsMatch` 对象，作用于全部 `tree` 节点。章节不划分挂接范围。成功目标是最底层单位工程；第二轮比较的直接父节点只用于筛选和核对。

| 字段 | 类型 | 语义 |
|---|---|---|
| `scope` | string | 固定 `FILE` |
| `executionStatus` | string | `SUCCEEDED`、`FAILED` 或 `NOT_RUN`，表示 CBS 子任务技术状态 |
| `cbsMatchStatus` | string | `"1"` 表示自动匹配成功；`"0"` 表示没有可采用的自动挂接 |
| `projectCbsId` | string或null | 唯一选中的单位工程叶子 ID；未挂接时为 null |
| `parentCbsNodeId` | string或null | 成功目标的直接父节点 ID；未挂接时为 null |
| `contextId` | string | 同一份匹配证据的规范化 JSON 摘要 |
| `reasonCode`、`reason` | string | 结果代码及可供人工核对的简短说明 |
| `evidenceRefs` | array[string] | 依据路径，如 `header.engineeringPart`、`header.siteName`、`internalSections.S1.title` |
| `stageOne` | object | `executionStatus` 及 `candidateLeafIds`，保留 match 和 possible 候选 |
| `stageTwo` | object | `executionStatus` 及 `evaluatedLeafIds`，成功执行时等于第一轮候选集合 |

阶段执行状态为 `SUCCEEDED`、`FAILED`、`SKIPPED`；没有第一轮候选时第二轮为 `SKIPPED`，`evaluatedLeafIds=[]`。每轮逐候选的判断和引用由服务保存，模型契约见第 7 节。公共结果无需重复传完整表头和所有模型原文。

`reasonCode` 包括 `MATCHED`、`NO_LEAF_CANDIDATE`、`NO_PARENT_MATCH`、`AMBIGUOUS`、`INSUFFICIENT_EVIDENCE`、`SCOPE_CONFLICT`、`CBS_EXECUTION_FAILED`、`CBS_INPUT_INVALID`、`CBS_OUTPUT_INCONSISTENT`。前六种是业务结论；后三种属于技术、输入或模型输出校验问题，不能写成语义“不匹配”。部分解析但不影响匹配证据时允许判断；匹配证据本身缺失或范围冲突时不得自动挂接。

`CBS_OUTPUT_INCONSISTENT` 表示首轮同名候选的 judgment 冲突。服务在筛选前按 `leaf_name.strip()` 校验，不将名称相近但不相同的候选并组，也不合并 ID。冲突时直接保树发布：文件执行 `SUCCEEDED`，semanticStatus 沿用来源树质量，CBS `FAILED`，目标 ID 均为 null，首轮 `FAILED` 且 `candidateLeafIds=[]`，第二轮 `SKIPPED` 且 `evaluatedLeafIds=[]`。空集合表示没有通过校验的候选检查点，不表示语义判断为无候选。原始评价单独保存，issues 携带冲突 ID、名称和判断，完整结果见[冲突示例](examples/build-result-cbs-inconsistent.json)。本版不对该已形成未挂接结果自动重试，用户通过现有“挂接”功能处理，或按原版本规则发起新构建。

`cbsMatchStatus="1"` 必须同时满足：首轮同名一致性校验通过，两轮成功且两轮 `context_status` 均为 sufficient，目标属于第一轮候选且第一轮为 match，第二轮对其父节点为 match，第二轮不存在其他 match 或 possible 候选，目标确为当前 CBS 快照中的单位工程叶子，父 ID 与快照一致。同一父节点下面仍有多个候选时，不能只根据父名称命中就任选叶子。

业务原因按范围冲突、证据不足、无候选或无父匹配、候选歧义的顺序判定，避免将已识别的范围冲突简化为“无候选”。技术失败在业务判断之前单独处理。`context_status` 是模型对本轮证据的判断，程序还需结合解析警告和来源完整性复核，不能仅凭模型声称 sufficient 就忽略已知的关键缺失。

`cbsMatchStatus="0"` 时返回空目标 ID，保留完整 `tree`、来源去向和原因。Java 将文件显示在现有“未挂接”页签，用户可通过“挂接”按钮选择 CBS。未挂接是正常业务状态，不新增“待确认”挂接状态。

`semanticStatus` 只反映来源树的结构、分类、数量与解析完整性，与 CBS 挂接状态独立。仅 CBS 未匹配、同名冲突或技术失败，不得把 READY 改为 REVIEW。已有来源问题导致 REVIEW 时继续保留该值。若 CBS 调用失败而树合法，文件 executionStatus=SUCCEEDED，cbsMatch.executionStatus=FAILED，原因作为诊断返回；页面仍归入“未挂接”，不是整份料表处理失败。未取得合法结构的文件仍为文件执行失败，不能生成假树。

### 5.4 Java 接收的闭环

Java 提交构建后取得 jobId，查询到文件终态，再调用文件结果接口取得 `tree + cbsMatch + rowDispositions + issues`。Java 验证版本和完整性后保存，再向前端提供展示数据。构建受理响应、Dify End 回执和服务端存储都不能代替这个结果响应。完整示例见[成功返回](examples/build-result.json)及[未挂接但返回完整树](examples/build-result-unmatched.json)。

## 6 模型输入与输出

### 6.1 输入包

AI 服务按文件建立 `packet_id` 和短行号映射。原业务 UUID 留在服务端，模型主要引用 `r`。输入包包含以下内容。

| 字段 | 内容 |
|---|---|
| `packet_id` | 不可变输入包标识，程序生成 |
| `context` | 完整表头、项目、场区、专业、表格边界、表类型 |
| `classification_rules` | 企业规则版本、原文、条件和例外 |
| `confirmed_decisions` | 当前文件适用的人工确认，仅由可信服务数据生成 |
| `rows` | 每行的 `r`、原序号、名称、规格、数量、单位、备注、表标识和可用版式证据 |
| `parse_warnings` | 输入未识别区域、字段缺失和绑定歧义 |

模型输入不含后续定额候选和价格，也不要求阅读整本设计说明。仅当当前结构或分类依赖额外供货说明时，把已定位且有来源的说明加入输入；没有材料时明确缺失，不从常识补成事实。

### 6.2 输出契约

模型输出顶层为 `packet_id` 和 `rows`。每个输入 `r` 恰好出现一次。原十字段继续保留，新增 `node_type` 与 `classification`。可配置的 JSON Schema 见[模型输出 Schema](model-output.schema.json)，System 提示词见[模型提示词](04-模型-System.md)。

| 字段 | 含义 |
|---|---|
| `r` | 当前输入包短行号 |
| `role` | 原始行的十种角色之一，包含新增的 `project` |
| `parent` | 结构父行，整数或 null |
| `inherit` | 补充共同名称的祖先行，按祖先顺序排列 |
| `qty_from`、`unit_from` | 引用其他行数量或单位，null 表示采用本行，不表示自动向上查找 |
| `quantity_basis` | `total`、`per_parent`、`unknown`、`not_applicable` |
| `quantity_parent` | per_parent 的数量基数祖先，其他口径为空 |
| `quantity_basis_ref` | 原文“每套”等口径依据所在行，无依据时为空 |
| `reason` | 结构或数量疑点的简短说明，不要求输出长推理过程 |
| `node_type` | 实物行为 `EQUIPMENT`、`MATERIAL` 或 null；其余角色为 null |
| `classification` | `status`、`rule_ids`、`source_rows`、`reason` |

模型 `classification.status` 为 `resolved`、`review`、`not_applicable`。模型的 `node_type` 专用于实物分类；`project` 的 `node_type=null`、`classification.status=not_applicable`，程序将 `project` 映射为最终业务类型 `PROJECT`，将 `section`、`group`、`summary` 映射为 `SUBSECTION`。最终工程及分部节点的 classification 标为 RESOLVED 并记录角色映射依据。`item` 等实物行不能标 not_applicable 来逃避分类。

### 6.3 角色与输出映射

| 模型角色 | 业务输出 | 数量处理 |
|---|---|---|
| `project` | `PROJECT` | 工程范围容器，quantity 为空，不计量 |
| `section` | `SUBSECTION` | 不计量，保留章节及范围 |
| `group` | `SUBSECTION` | 共同名称不重复计量 |
| `summary` | `SUBSECTION`，保留汇总参考 | `quantity=null`，明细分别计量 |
| `item` | `EQUIPMENT`、`MATERIAL` 或分类待确认 | 从合法来源取量 |
| `assembly` | `EQUIPMENT`、`MATERIAL` 或分类待确认 | 整套数量独立保留 |
| `component` | `EQUIPMENT`、`MATERIAL` 或分类待确认 | 保留组成件及每套口径，不与父项数量相加 |
| `attribute` | 所属节点的 attributes | 不产生计量节点，实物数量不能藏入属性 |
| `note` | 所属节点的 notes，或文件说明 | 不产生计量节点 |
| `pending` | 可见待确认节点，`type=null` | 原值保留，不补造确定总量 |

未挂接的属性、说明和 pending 仍有行去向记录。无法确认父节点的 pending 在文件待确认根区域展示，不自动挂到上一个实物对象。

## 7 Dify 精简节点契约

本节替代原 57 节点配置。具体 22 节点绑定见[逐节点配置参考](07-Workflow逐节点配置参考.md)，完整旧新去向见[节点清单](workflow-node-inventory.json)。清单是设计，不是可导入 DSL。

### 7.1 执行边界

一个 dispatch 只绑定一份 file job。AI 服务持久阶段状态是下一步动作的唯一依据；Dify 只按服务动作串行调用三个模型节点。批量队列、权限、全局限流、技术失败记录、恢复、文件对账和最终结果发布在 AI 服务。

首轮结构与一次纠正复用 sLLM。纠正需要原始完整输入、首轮提案和具体错误，使用独立的 STRUCTURE_REPAIR 阶段。REPAIR_REQUIRED 不是文件终态；正常 End 后调度器主动安排纠正，不等待异常监控器。只有业务输出可修复时才纠正；技术重试使用独立预算。

### 7.2 入口、阶段与内部接口

Start 仅接收 `dispatch_id`。AI 服务预先保存对应 file_job_id、fileId、快照版本、执行配置版本和授权范围。入口 claim 必须原子绑定真实 Dify 运行；同 dispatch 的重复 run 不能同时取得执行权。实际运行 ID 的变量及停止接口必须在部署中确认，不能编造选择器。

| 接口 | 请求 | 服务持久行为与返回动作 |
|---|---|---|
| POST `/internal/quantity/dispatches/{dispatch_id}/claim` | 服务认证、派发身份、实际运行身份 | 原子领取；返回文件身份、entry_phase、当前 input_json/attempt_id。入口为 STRUCTURE_INITIAL、STRUCTURE_REPAIR、CBS_LEAF、CBS_PARENT、RETURN |
| POST `/internal/quantity/files/{file_job_id}/process-text` | 完整模型原文、当前 attempt 身份 | 校验与保存结构、一次纠正计划或结构失败；next_action=CBS_LEAF/RETURN |
| POST `/internal/quantity/files/{file_job_id}/cbs-leaf/prepare` | 派发及实际运行身份 | 回读结构、固定完整证据、容量检查、幂等准备 attempt；RUN_LEAF/RETURN |
| POST `/internal/quantity/files/{file_job_id}/cbs-leaf/text` | 首轮完整模型原文、attempt 身份 | 校验覆盖、引用与候选；持久首轮结果及父轮准备状态，或发布完整未挂接树；CBS_PARENT/RETURN |
| POST `/internal/quantity/files/{file_job_id}/cbs-parent/prepare` | 派发及实际运行身份 | 回读同一证据和已保存候选，校验容量/状态，准备 attempt；RUN_PARENT/RETURN |
| POST `/internal/quantity/files/{file_job_id}/cbs-parent/text` | 第二轮完整模型原文、attempt 身份 | 校验后生成并发布不可变文件结果；RETURN |

这些接口均为拟实现新契约，不能只改画布 URL 而继续调用旧包装接口。准备和领取接口可能写状态，因此使用 POST 并定义幂等键；网络重传不能再次分配尝试或重复消耗预算。

首轮同名判断冲突由 `cbs-leaf/text` 保存原输出并发布完整未挂接结果，返回 HTTP 200、`status="1"`、`next_action="RETURN"`、`stage_status="OUTPUT_REJECTED"`、`reason_code="CBS_OUTPUT_INCONSISTENT"`、非空 `file_result_ref` 和 `result_revision`。HTTP 成功表示校验及发布动作完成，不表示模型匹配成功。若发布未完成，则由持久待办恢复，不能先返回上述成功响应。

公共头：Authorization Bearer、X-Quantity-Dispatch-Id、X-Quantity-Run-Id、X-Quantity-Workflow-Id、X-Quantity-Execution-Config-Id。后两者分别绑定实际执行的 Workflow 版本和新应用的冻结配置标识，详见 7.4。模型提交另带 X-Quantity-Attempt-Id。attempt 由服务准备阶段分配并冻结 packet、context、候选、规则及执行配置，提交方不重传可篡改候选名单。模型返回 packet_id/context_id 仍必须与冻结快照核对。

模型提交的 Content-Type 为 `text/plain; charset=utf-8`，HTTP raw body 直接绑定模型节点完整 text；不拼接 JSON 外壳、不额外套引号。服务保存原文后作完整 JSON、Schema 和业务校验。截断文本不得提取部分 rows 冒充成功。只有 structured_output 而无完整 text 的插件，保留三个序列化适配 Code（总 25 节点）产生完整 JSON 文本；是否提供该变量须实测。

内部响应继续是 `{"status":"1","data":{...}}`。reader 核验 HTTP、status、文件/派发/运行身份、允许动作以及当前输入引用，再输出已声明类型。未知动作抛错；不能用普通 ELSE 掩盖非法动作。具体响应字段以 07 为统一配置表。

### 7.3 终态、发布与统一恢复

End 只输出 dispatch_id 和入口已验证的 file_job_id，不引用互斥分支输出，也不承诺文件已完成。AI 服务对正常结束、失败、中断和没有 End 的运行都回读持久阶段。

准备接口或 CBS 首轮校验已可确定无匹配/容量问题时，回读合法结构并发布完整未挂接结果。父轮校验接口承担最终发布。技术重试耗尽由服务恢复器发布：无合法结构为 FAILED/UNAVAILABLE；有合法结构但 CBS 技术失败时文件 executionStatus=SUCCEEDED，semanticStatus 沿用来源树质量，cbsMatch.executionStatus=FAILED。技术错误不能冒充语义不匹配。

阶段保存与发布使用同一数据库事务或持久发布待办，保证“阶段已保存、完整结果未生成”可以继续 finalize 而不重跑模型。所有发布入口调用同一服务发布函数；同 file job 只生成一次自动终态，响应丢失回读原版本。对象存储先写不可变对象，确认可读后再提交结果引用；不能先发布引用后生成数据。

成功与失败争用同一阶段时按状态、attempt 和租约条件提交。已有成功快照不能被迟到失败覆盖；发布后迟到结果只留执行记录。终态后的修改通过新的 buildGeneration，不能在同代次任意生成多个可覆盖结果。

服务端恢复位置可直接选择 CBS_PARENT，并由父轮 prepare 回读完整输入，不依赖本次未执行的首轮变量。现画布不再放失败回执链、批量对账链和重复 finalize 节点，以上服务职责因此成为必要交付。

### 7.4 Dify 调用、运行身份与固定版本

AI 服务在首次派发前为 file job 冻结 `execution_config_id`。该配置记录 `pin_mode`、`dify_api_base`、`dify_app_id`、服务端 `credential_ref`、已发布的 `workflow_id`，以及提示词、Schema、模型参数、规则和组装代码版本及摘要。配置不可原地修改；纠正和技术恢复继续引用同一配置。密钥本身不进入运行记录或 Java 业务响应。

| pin_mode | 调用方式 | 版本约束 |
|---|---|---|
| `WORKFLOW_ID` | POST `{dify_api_base}/workflows/{workflow_id}/run` | 目标部署支持指定已发布版本时使用；版本不可用则停止自动派发，不降级为当前发布版本 |
| `IMMUTABLE_APP` | POST `{dify_api_base}/workflows/run` | 每个执行配置使用独立 Java 应用版本及凭据引用；存在排队、在途或待恢复任务时不修改其发布版本、环境变量或模型配置 |

两种方式都固定 `response_mode="streaming"`，请求体为 `inputs={"dispatch_id":"..."}`、`user=<可信稳定标识>`。指定 Workflow 版本的 API 不能自动冻结外部模型凭据、环境变量或供应方配置；这些共享设置也须保持兼容且不可随意变更。需要改变时使用新的执行配置，必要时创建新的 Java 应用版本，保留旧版本服务原任务。现有原 Workflow 始终保持不变。[运行 API](https://docs.dify.ai/en/api-reference/workflow-runs/run-workflow)、[指定版本 API](https://docs.dify.ai/en/api-reference/workflow-runs/run-workflow-by-id)

每次实际调用独立保存以下记录。一个 dispatch 如出现重复启动，所有观察到的 run 都记录，只有 claim 成功者有执行权，不能用后到事件覆盖获准运行。

| 字段 | 来源与用途 |
|---|---|
| `dispatch_id`、`file_job_id`、`execution_config_id` | 调用前保存的可信派发记录 |
| `dify_api_base`、`dify_app_id`、`credential_ref`、`dify_user` | 冻结配置及实际调用参数；后续查询与停止使用同一调用身份 |
| `workflow_id` | 预期的已发布版本 ID，首次执行、纠正及恢复均相同 |
| `observed_workflow_id` | 实际运行的版本，来自 Dify 系统变量和实际返回信息，与预期版本核对 |
| `workflow_run_id` | 实际运行记录 ID，用于运行查询及 claim，不用于停止路径 |
| `task_id` | 从当前调用的实际 SSE 事件取得，用于停止在途任务；尚未取得为 null，禁止由 run ID 推导 |
| `stop_requested_at`、`stop_acknowledged_at` | 停止请求与确认时间，不等同于运行终态或模型停止证明 |
| `run_terminal_confirmed`、`model_termination_confirmed` | 运行终态与远端模型占用的查证记录，分别管理对应预算 |

`qClaimRun` 及后续内部 HTTP 增加 `X-Quantity-Workflow-Id`，绑定当前实际版本变量（目标部署核对 `sys.workflow_id`）；增加 `X-Quantity-Execution-Config-Id`，绑定新应用静态环境变量 `QUANTITY_EXECUTION_CONFIG_ID`。服务认证限定应用范围，并将这些值与 dispatch 的冻结配置比较。版本或配置不符返回 HTTP 409、`EXECUTION_VERSION_MISMATCH`，不返回模型输入。claim 响应回显 `workflow_id` 和 `execution_config_id`，已有 reader 同步核对。服务再用真实运行事件或查询结果核对实际版本；不能只保存版本标签却不参与校验。

claim 可能先于 SSE 身份入库到达。task_id 尚未取得不阻塞已经核验的 claim；两条路径按当前调用记录和 workflow_run_id 关联后补齐，发现冲突即隔离查证。旧 dispatch、新版本或重复 run 不得读取当前任务的输入。

停止请求为 POST `{dify_api_base}/workflows/tasks/{task_id}/stop`，body=`{"user":"<原 dify_user>"}`，使用原应用凭据。task_id 缺失时不发送停止请求，先按已知 run 查证；两种身份均未知时保留占用并进入有界查证及人工处理，不能盲目重派。HTTP 200 或 `result=success` 仅记录停止确认。查询到运行终态后才释放运行槽；远端模型仍不明确时继续保留对应模型预算。再次执行须同时满足执行权检查和模型预算许可。[停止 API](https://docs.dify.ai/en/api-reference/workflow-runs/stop-workflow-task)

上述登记、停止和固定版本在 AI 服务及已有节点配置中完成，不新增画布节点。跨运行配置不一致不得用新提示词重新生成旧阶段并声称是同一次恢复。

### 7.5 容量与调用次数

正常文件一次 run 依次执行结构、CBS 首轮、CBS 二轮，三次模型调用。需要语义纠正时另一次 run 从纠正阶段继续，共四次模型调用；技术重试另计。一次 run 只处理一个文件，模型阶段串行。

全服务最多 4 个活跃单文件运行是待测初值，取消原 2 个 dispatch × 批内 2 的配置。其他应用、远端未停止请求和供应方 RPM/TPM 须计入总限流。

完整输入、模型预期输出、HTTP body 和 Code 字符串都需检查容量。结构输入超限且尚无合法树时返回 FAILED/UNAVAILABLE 与 PACKET_TOO_LARGE；已有合法树但 CBS 超限返回未挂接并保留树。跨包父子拼接未在本版实现。

## 8 程序校验

| 检查对象 | 通过条件 | 不通过时的结果 |
|---|---|---|
| 身份与版本 | 请求、文件、packet、规则版本一致 | 拒绝该次提交，不影响其他文件 |
| 行覆盖 | 每个输入行恰好一个角色判断，有可追溯去向 | 结构纠正，仍失败则文件不可提交 |
| 父子引用 | 节点存在、同文件、无自引用和循环 | 结构纠正或失败 |
| 继承关系 | 仅合法祖先提供缺少的共同身份 | 纠正并保留原名，禁止借用相邻规格 |
| 字段来源 | 名称、规格、数量和单位能回到原行或单元格 | 节点待确认，不编造缺失字段 |
| 分类 | 枚举合法、规则存在、条件依据无明确冲突 | 保留分类待确认，不回退关键词默认分类 |
| 工程与分部 | project 映射 PROJECT，section/group/summary 映射 SUBSECTION，有原文范围依据且不计实物数量 | 保留结构疑点，不能把实物改成工程规避分类 |
| 总分数量 | 同口径、同单位下可校核，父量不重复计入 | 数量待确认，结构对象仍保留 |
| 每套用量 | 有限定依据和实物数量父项，基数单位一致 | 保留原量，quantity 为空，数量待确认 |
| 实物覆盖 | 每个实物数量来源有独立对象、汇总依据、组成依据或可见问题 | 文件 REVIEW，禁止漏行 |
| CBS | 属于请求项目、当前版本的单位工程叶子 | 未挂接或拒绝非法 ID |
| 两轮证据 | context_id 与服务快照一致，两轮 match_context 内容相同 | 拒绝变更上下文的提交 |
| 首轮同名一致性 | 同一 match_context 下，leaf_name 仅去除首尾空白后相同的候选，其 judgment 一致；每个 ID 仍恰好一次 | 持久化 CBS_OUTPUT_INCONSISTENT，发布完整树及未挂接结果，不进入第二轮 |
| 两轮候选 | 第二轮集合等于首轮保留集合，父节点来自可信快照，结果唯一 | 未挂接或阶段失败，保留合法来源树 |
| 文件范围 | 全文件只有一个挂接结果，内部章节没有被另行挂接 | 拒绝多个目标，不删除来源节点 |
| 返回树 | children 与父键一致，节点覆盖完整且顺序确定 | 不发布损坏或截断树 |

模型缺资料与技术输出损坏采用不同结果。结构损坏不能发布半棵树冒充完整结果。合法树中的局部业务疑点可以展示与人工处理。

## 9 Java 保存和展示约定

Java 的持久后台任务负责取回并应用结果，不依赖页面保持打开。Java 在短事务内校验文件仍存在、批次未锁定、构建代次仍当前、CBS 与规则版本一致、人工修订未改变。校验与正式写入在同一事务或等效并发控制中完成。

Java 先收齐 `tree` 并遍历节点，核对嵌套关系与父键一致。所有节点先分配 UUID，建立 `resultKey → UUID` 映射，再写 `parent_id`。同级顺序按 `sortNo` 保存。来源行关联可使用独立来源表或结构化扩展字段，具体数据库迁移在实施时确定，但不能只存在日志中。

Java 把 `cbsMatch` 保存为文件级挂接结论。成功时再次检查目标叶子和直接父节点关系，将该文件所有来源节点关联到同一个单位工程；未成功时保存未挂接树。任何已有人工修正都先按版本冲突处理，不由自动匹配覆盖。

`PROJECT` 和 `SUBSECTION` 不参与设备材料工程量合计，也不能作为每套用量的实物数量父项。`summaryQuantity` 仅作核对。`PER_PARENT` 只通过明确数量父项进行乘法，Java 复算结果与 AI 服务 Decimal 结果不同则拒绝自动确认。单位变换保留公式及换算依据，未配置换算关系时不自动换算。

文件来源子树与固定分组分开保存。删除文件仅删除该文件的来源树、挂接关系和派生结果。共享固定分组按是否仍有其他文件使用决定是否保留。重复导入同一 `jobId + fileId + resultRevision` 不新增节点。

不同文件同时写入同一个 CBS 时，事务只替换各自文件的来源记录，不能先清空该 CBS 的全部工程量。固定分组使用项目、CBS 节点和分组类型的唯一约束，并发冲突后复用已有分组。文件版本和人工修订检查与入库在同一短事务内完成，模型运行期间不持有数据库行锁。

待确认节点在 Java 结果暂存或允许空类型的节点模型中保留。是否进入步骤3同时检查需求文档已有的 CBS 挂接条件，以及新增的影响后续处理的结构和类型问题。普通备注提示不阻断。具体阻断项使用问题代码声明，不能用一个 REVIEW 状态把整批全部拦住。

## 10 与接口讨论稿的变化

| 原约定 | 本方案 | 原因 |
|---|---|---|
| 一次 HTTP 等待整批结果 | 异步 job，按文件取回 | 批量耗时不依赖单次连接存活 |
| rawItemId 不回传，不保存关联 | 返回并保存行去向及字段来源 | 支持合并续行、数量对账和人工回查 |
| 只有三个必填节点类型 | 工程、分部、设备、主材四种确定类型，加可空待确认状态 | 支持来源工程范围，资料不够时不强行分类 |
| type 表达全部含义 | 增加 semanticRole、成套归属和数量口径 | 父子层级与计量含义分开 |
| 每节点填写 CBS | 全文件一个 cbsMatch，所有节点继承 | 整张料表挂到同一单位工程 |
| 未固定 CBS 匹配顺序 | 先单位工程名称，后候选直接父节点名称，两轮同一份料表证据 | 符合用户确认的语义筛选顺序 |
| 仅返回父键节点列表 | 对外返回 children 嵌套树，程序保留一致的父键 | Java 直接收到完整树数据 |
| quantity 为模型建议值 | 模型返回来源及口径，程序回读并计算 | 避免改写、重复与无依据乘法 |
| 输入仅平铺业务字段 | 增加原始规格、逐表列定义、单元格与解析警告 | 支持 DOC 合并行及 PDF 表格 |
| Java 生成正式 ID 和固定分组 | 保留 | 与需求文档一致 |

HTTP 400 表示结构或类型不合法，422 表示请求业务约束不满足，409 表示幂等输入冲突或结果版本过期，429 表示限流，503 表示依赖暂不可用。业务未挂接或分类待确认不是 HTTP 500。
