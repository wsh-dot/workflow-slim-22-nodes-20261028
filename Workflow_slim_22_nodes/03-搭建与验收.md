# 搭建并验收精简版 Java 与 Dify 工程量结构联调

本文按[方案说明](01-方案说明.md)、[接口与节点契约](02-接口与节点契约.md)实施。目标是把 Java 已解析的料表转成有来源、有分类和父子关系的完整工程量树，完成文件级两轮 CBS 匹配，再由 Java 校验、保存并展示。定额、价格和金额计算仍属于后续业务阶段。

本版采用 **22 个核心节点**的独立新 Workflow。三个模型节点分别处理结构与分类、CBS 单位工程名称、CBS 直接父节点名称。模型提供完整 `text` 时，HTTP 原样提交文本；部署只提供 `structured_output` 时增加三个序列化节点，使用 **25 个节点的兼容版**。原 Workflow 保持原样。本文是待实施与待执行的验收要求，不表示真实模型、部署或业务验收已经通过。

## 1 固定联调基线与范围

1. 只读导出现有 Workflow，记录旧应用身份、节点、连线、提示词、配置及发布版本。新建独立 Java 专用应用，使用独立 App ID 和 API Key。
2. 核对实际部署的 Dify 版本、模型插件、三个模型节点的输出变量、最大输入输出容量和 HTTP raw body 绑定能力。记录采用 22 节点版还是 25 节点兼容版。
3. 确认真实 workflow_run_id、task_id、workflow_id 可分别登记。固定 streaming 调用，验证停止使用 task_id 和原 user；claim 在实际版本或 execution_config_id 不符时拒绝提供模型输入。
4. 固定 `quantity-build-v1` 接口及 `semantic-java-quantity-v1` 结构模型契约，分别记录提示词、Schema、模型与企业规则版本。按 02 §7.4 选择 WORKFLOW_ID 或 IMMUTABLE_APP，将配置用于实际调用及恢复校验。
5. 取得企业确认的设备材料划分规则、适用条件、例外和标注样本，记录版本及摘要。

企业规则发布包或标注样本未提供时，可以先用明确标为 `DEMO-ONLY` 的规则和固定 JSON 验证接口、组装和校验。这样的结果不能说明设备材料分类或 CBS 语义匹配已满足业务要求。本次从本机旧版方案补齐 15 份合成 `examples/`，另增同名冲突及运行身份样例；来源见 examples/README.md。

## 2 建立 Java 原始行输入

1. 为文件、表格、原始行和可识别单元格保存标识及修订，保证同一输入快照中的引用稳定、唯一且可回查。
2. 按每张表自己的列定义提取名称、独立规格、数量、单位和备注，不套用其他表的列映射。
3. 完整提取表头项目、场区、工程部分和专业，保留表头原文；提取“一、（一）、（二）”等内部章节、序号和原始行来源。
4. 保留非空章节、属性续行、范围说明及合并来源，把章节同步建为 `internalSections` 索引。需要进入来源树的工程标题必须有真实原始行，匹配背景不自动生成工程根。
5. 提供当前项目 CBS 快照，包含全部合法单位工程、直接父节点及其真实 ID、名称和关系；同名不同 ID 不去重。
6. 将解析遗漏、OCR 疑点、跨页续表不确定和列绑定问题写入 `parseWarnings`、`coverage`，不能用空字段伪装完整解析。
7. 按[接口与节点契约](02-接口与节点契约.md)准备固定请求 JSON，逐项核对字段、顺序、来源及版本，再接入模型。

先分别验证 DOC、DOCX、可复制文字 PDF 和扫描 PDF 的解析输入。模型只能分析进入输入包的内容；未读区域须保留明确状态。`parseStatus=PARTIAL` 的文件不得声明整文件完整，`FAILED` 的文件不调用结构模型。

## 3 在 AI 服务落实任务状态与数据适配

新增能力通过独立路由和新契约实现。旧应用继续使用原接口、提示词与 Schema；复用共享算法模块时，同时检查旧入口的兼容行为。

1. 接收 Java 构建请求，保存不可变输入、CBS 与规则快照，建立请求幂等记录及逐文件任务。
2. 为每个文件保存 `r → rawItemId → fieldSources` 映射，建立适用于新契约的输入包和组装适配层。
3. 解析并保留 `project`、`node_type`、`classification` 等新字段。旧组装器不认识 `project` 时，只在兼容层内部按非计量容器处理，最终恢复 `PROJECT`，不能静默降格或丢字段。
4. 保存逐阶段输入、完整模型输出、校验结果及成功检查点。阶段提交使用当前文件、快照和尝试身份实现幂等，重复响应不能再次生成业务节点或再次消耗修复次数。
5. 批量排队、运行限流、失败登记、阶段恢复和对账由 AI 服务承担。Dify 每次运行只处理一个文件及其当前剩余阶段，画布不再包含批量 Iteration、全批汇总或独立失败登记长链。
6. 服务根据持久状态为下一次运行确定 `entry_phase`，不能依赖模型建议或前端自报阶段恢复。
7. 构建完整来源树和文件结果，提供按版本读取实际 JSON 的对外接口。结果发布和 Java 导入都以持久数据及完整性校验为准。

不能把 Java JSON 直接交给依赖旧解析目录的入口，也不能让旧归一化函数丢弃新字段。批量与恢复移到服务后，身份核对、来源核对、行覆盖、CBS 校验和确定性计算仍然必须执行。

## 4 先用固定 JSON 验证契约

在真实模型调用之前，用人工编写且注明用途的请求、结构输出、两轮 CBS 输出及预期文件结果，验证服务的正常与拒绝分支。固定样例验证的是程序能否按契约处理数据，不是模型质量。

至少检查以下内容：

- 每个输入 `r` 恰好一次；所有父子、继承、数量和分类来源引用均存在；无跨文件引用、自引用或循环。
- `project/section/group/summary` 与实物角色按契约映射；属性、说明有明确归属和内容；未知分类不能默认保存为主材。
- `resolved/review/not_applicable` 与实物类型、规则编号、来源依据符合约束，不能用空依据的 `resolved` 绕过待确认。
- 汇总参考量不参加计量；多规格独立取量；合并单元格按物理来源核查，不能按相同文字去重。
- 每套计算有合法实物数量父项和原文或可信确认依据；本版不能可靠表达的“每 N 套”或单位换算，保持数量待确认，不能按每一套直接相乘。
- 两轮 CBS 使用同一完整 `match_context` 和摘要；第一轮覆盖全部合法候选，第二轮覆盖第一轮保留集合，直接父节点来自可信快照。
- 相同单位工程名称的不同 ID 不得因没有区别依据的首轮判断被任意筛成唯一目标；范围冲突、已知关键缺失和剩余歧义不得自动挂接。
- `tree.children` 与父键一致；来源、行去向、数量和版本可对账；匹配状态变化不能减少合法来源树节点。

按下列顺序记录结果，不能把后一层的未执行写成已通过：

| 验证层 | 执行内容 | 能证明的范围 |
|---|---|---|
| 文档和图清单 | 运行 `verify_simplified.py`，核对 22 节点图、原节点去向映射、可选 25 节点版及原附件保留 | 当前文档与清单的一致性 |
| 固定 JSON | 调用新服务校验、组装、状态转换和结果接口 | 确定性业务约束及接口行为 |
| 真实模型 | 对企业确认样本运行三个模型阶段，逐项比对答案 | 样本范围内的结构、分类和 CBS 质量 |
| 部署与 Java 闭环 | 运行新 Workflow、模拟恢复、完整取回结果并入库展示 | 当前部署版本和实际链路行为 |

在本目录执行本版检查：

```bash
python verify_simplified.py
python verify_examples.py
python verify_regressions.py
```

`verify_examples.py` 校验已补齐的合成样例，并增加同名误筛反例。`verify_regressions.py` 校验冲突保树未挂接、停止身份、版本绑定及拒绝分支。缺少必需样例时明确失败或 NOT_RUN，不将其计为通过。这些脚本只验证本地契约样例，不连接真实服务。

## 5 配置三个模型及原文提交

三个模型节点的任务和输出契约不同，不合并为一个通用 Schema：

| 模型阶段 | System 来源 | 输出 Schema | 服务职责 |
|---|---|---|---|
| 结构与企业分类，首轮和修复共用 | [结构 System](04-模型-System.md) | [结构输出 Schema](model-output.schema.json) | 校验每行判断，组装合法结构，决定是否需要一次修复 |
| CBS 第一轮：单位工程名称 | [CBS 两轮提示词](05-CBS两轮匹配提示词.md)第一轮 | [CBS 首轮 Schema](cbs-leaf-output.schema.json) | 校验全覆盖，保留候选，准备直接父节点输入 |
| CBS 第二轮：直接父节点名称 | [CBS 两轮提示词](05-CBS两轮匹配提示词.md)第二轮 | [CBS 第二轮 Schema](cbs-parent-output.schema.json) | 校验候选、父子映射、证据及唯一目标，形成文件级结论 |

模型 User 消息仅绑定服务返回的完整输入字符串。修复运行仍使用同一个结构模型节点、System 和 Schema，输入包含原包、首轮提案及明确错误，要求返回完整 `rows`。缺原文或规则不是靠修复编造内容的理由。

**22 节点版的提交方式：**模型能提供完整 `LLM.text` 时，后续 HTTP 选择 raw body，直接绑定该文本，设置 `Content-Type: text/plain`，按 UTF-8 发送。不额外加引号，不拼装外层 JSONObject，不把模型文字插入手写 JSON 模板。URL、请求头及服务已登记的运行上下文负责身份绑定；模型文本不能决定所属任务、阶段或规则版本。

**25 节点兼容版：**只有 `structured_output`、没有可用完整 `text` 时，三个模型各增加一个序列化节点，用标准 JSON 序列化器把对象转成完整字符串，再交给相同的 HTTP 原文提交入口。不能绑定不存在的 `text`，不能用字符串拼接代替序列化，也不能把空对象当成成功输出。

服务收到完整文本后严格解析并执行新 Schema 和业务校验。截断、无效 JSON 和模型错误必须有明确状态。供应商参数、用量和结束原因按实际可用字段记录；不假设低温度或结构化输出可以保证业务正确。

## 6 接好 22 节点主干与恢复入口

逐节点配置以[新 Workflow 搭建步骤](06-Workflow改造操作步骤.md)和[节点配置参考](07-Workflow逐节点配置参考.md)为准。精简后的正常路径仍然是“结构理解 → 程序校验 → CBS 首轮 → 程序校验 → CBS 二轮 → 程序校验与结果保存”。一个条件完整的普通文件在一次运行中完成三次模型调用。

### 6.1 Start、claim 与 reader

Start 只接收服务派发的 `dispatch_id`。先调用 `claim`，由服务原子核对派发、当前文件、快照、有效执行租约和此次真实 `workflow_run_id`，完成实际运行登记，再返回阶段入口及输入。旧派发、跨文件、重复占用或过期运行不能继续写结果。

`qReadRunState` 必须校验 HTTP 状态、业务状态、JSON、身份及 `entry_phase`。各阶段 HTTP 后的 reader 同样保留，不能把省节点理解为直接信任 HTTP 200 或跳过文件、版本和上下文核对。未知阶段、无效引用、缺必要输入均须异常终止，交由服务对账。

| `entry_phase` | 允许执行的入口 | 必须满足的前提 |
|---|---|---|
| `STRUCTURE_INITIAL` | 结构模型首次判断 | 当前输入包完整可执行，首轮尚未形成成功检查点 |
| `STRUCTURE_REPAIR` | 复用结构模型作唯一一次修复 | 服务已保存首轮提案、具体错误及修复额度 |
| `CBS_LEAF` | CBS 单位工程名称模型 | 已有合法结构；跳过已成功的结构阶段 |
| `CBS_PARENT` | CBS 直接父节点名称模型 | 已有合法结构及已校验首轮候选；复用同一匹配上下文 |
| `RETURN` | 返回正常 End | 本次运行无需再调模型；是否终态仍由服务持久状态决定 |

### 6.2 一次结构修复由服务发起后续运行

首轮输出存在可修复结构错误时，服务先持久化 `REPAIR_REQUIRED`、原提案、错误清单和剩余修复额度，当前 Dify 运行走返回分支。`REPAIR_REQUIRED` 是非终态，文件执行状态可保持 `RUNNING`；不能把一次正常 End 当成文件已完成。

AI 服务确认旧运行已停止后，主动创建新 `dispatch_id`，继续同一 `file_job_id` 和构建代次，`entry_phase=STRUCTURE_REPAIR`。修复模型通过后，剩余 CBS 两轮在该运行继续执行。普通修复路径共两次运行、最多四次模型调用：首次结构一次，修复结构一次，CBS 两轮各一次。第二次结构仍不合法时记录无可用结构的明确失败，不能再次消耗修复额度或发布半棵树。

已持久化成功的阶段不重复调用模型。若成功阶段的 HTTP 响应丢失，服务从检查点选择下一入口；不能一律从结构首轮重跑。技术恢复另记尝试和费用，不把技术重试冒充新增结构修复。

### 6.3 End 与服务对账

正常 End 只返回 `dispatch_id` 和 `file_job_id` 身份。它不返回完整树，也不单独证明文件成功、匹配成功或任务终态。`RETURN` 只是当前运行的结束入口。

AI 服务对**正常结束和异常终止**都查询真实运行状态并对账持久检查点，确定下一次派发、业务终态或明确技术失败。流连接断开时先查运行，不把断流直接等同于运行停止。失败登记、超时处理和遗漏恢复都在服务中完成；画布发生错误而没有走到 End，仍必须由服务闭环。

## 7 校验来源、数量并接入 Java 保存

服务按原始行或真实单元格回读名称、规格、数量和单位。工程、分部、共同名称与汇总不额外计量；汇总仅保留参考量。属性和说明要保留内容及所属对象。无法确定的结构、分类和数量分别标记，任何实物数量来源都要有对象、合法汇总/组成关系或可见问题。

Java DTO、校验、存储约束和前端标识同步支持 `PROJECT`、`SUBSECTION`、`EQUIPMENT`、`MATERIAL` 及契约允许的待确认状态。界面将 PROJECT 显示为“工程”，固定“设备”“主材”分组仍为分部。

1. Java 查询文件终态后，通过 AI 服务结果 API 取得同一版本的完整 `tree + cbsMatch + rowDispositions + issues`。受理响应、Dify End 的两个身份字段及服务端已存储均不能代替实际返回 JSON。
2. 验证文件、构建代次、CBS、规则、人工修订和批次锁定；分页时收齐同一 `resultRevision` 的全部数据后再提交。
3. 遍历树核对父键与 `children` 一致、每个节点恰好一次，建立 `resultKey → UUID` 映射，保存父关系、同级顺序、类型、数量口径和持久来源关联。
4. 同一 `jobId + fileId + resultRevision` 重复导入不新增节点。获准重建时，按既定跨代身份及衍生引用策略处理旧记录，不能静默覆盖人工修正。
5. 保存文件级 CBS 结论。匹配成功时再次校验叶子与直接父节点，把文件来源节点关联到同一单位工程，并幂等创建“设备”“主材”固定分组；未匹配时保存未挂接来源树。
6. 以最外层实物类型放置整棵实物子树，保留组成件自身类型和原父子关系。混合纯分组可生成展示分支，但不复制实物记录，不把汇总参考量当作拆分后小计。
7. 未知类型和关系保留在可见的待确认结果中。文件删除、版本更新或人工修订后到达的旧结果按冲突处理。

有合法结构后，CBS 无候选、候选超限、业务歧义或技术失败都必须保留并返回完整树。**结构输入本身超限且没有合法结构时，结果为 `UNAVAILABLE`，不能用 `REVIEW` 暗示已经有可用树。** 已有合法树而 CBS 无法自动挂接时，文件执行为 SUCCEEDED，页面进入“未挂接”；semanticStatus 仅反映来源树质量，并单列 CBS 状态与原因。

## 8 验证核心业务案例

以下保留原 24 个业务场景。设备或主材结论以企业确认规则和专家答案为准，样例中的条件不能替代真实规则。

| 编号 | 输入或故障场景 | 验收重点 |
|---|---|---|
| 1 | 光伏组件及电压、电流属性续行 | 实物对象只生成一次；属性有正确归属、完整内容和来源；类型遵循企业规则。 |
| 2 | 共同名称下两种电缆规格 | 两个独立实物对象均保留，规格不丢，父分组不计量；类型按规则确定。 |
| 3 | 箱变总计 2 台及唯一规格 2 台 | 实物量仍为 2 台，父总量仅作核对参考。 |
| 4 | 多规格总分表，一条规格缺量 | 缺量为空，不把父总量复制给每条规格。 |
| 5 | 明确的成套设备与每套组成用量 | 组成件可展开、自身类型独立；有依据时乘法只发生一次，父子不同实物数量不相加。 |
| 6 | 名称完整的三种坡度支架 | 各自保留，不串成父子，不继承另一坡度的完整名称。 |
| 7 | 空序号但具有独立含义的防火涂料 | 不因空序号被错误并为上一项属性。 |
| 8 | 只有参数数字的属性行 | 参数保留为属性，不成为采购数量。 |
| 9 | 同名不同规格以及跨场区同名对象 | 不按名称或数量相同去重，不跨文件合并业务对象。 |
| 10 | 设备表中的材料类对象 | 类型依企业规则，不按表类型统一分类。 |
| 11 | 企业规则未覆盖或适用条件不足 | 分类待确认，原实物和已知结构保留，不默认主材。 |
| 12 | 混合设备与主材的纯分组，及设备下的主材组成件 | 固定分组展示不破坏实物子树、不复制计量对象。 |
| 13 | 不同父节点下同名“电气部分”单位工程 | 第一轮保留全部有相同匹配依据的 ID；第二轮读完整原证据比较直接父名称；最终目标为单位工程叶子。 |
| 14 | 部分 OCR 失败、跨页续表、重复表头和合并数量单元格 | 保留解析警告及来源，不重复计量；关键匹配证据缺失不得自动挂接。 |
| 15 | 土建工作量、施工便道或纯引用文件行 | 未定义类型的实物待确认，纯引用按说明处理，不强行归设备或主材。 |
| 16 | 第一轮没有 match 或 possible 候选 | 跳过第二轮，保留全部合法来源树及明确未挂接原因。 |
| 17 | 第一轮只剩一个候选，但直接父节点与料表不符 | 仍执行第二轮，不因候选唯一直接挂接。 |
| 18 | 两个候选属于同一个匹配父节点 | 不能按顺序任选叶子；同名叶子首轮不一致判断不能制造伪唯一。 |
| 19 | 第二轮上下文被缩为场区、候选越界或父 ID 被替换 | 服务拒绝错误阶段提交，完整合法来源树仍保留。 |
| 20 | 内部章节说明互相冲突的工程范围 | 一个文件级 `SCOPE_CONFLICT` 未挂接结果，不按章节拆成多个挂接目标。 |
| 21 | Java 完整取回匹配和未匹配结果 | 树节点数、角色、类型、数量、父子关系、来源和版本与持久结果一致。 |
| 22 | CBS 第二轮超时 | 服务登记技术失败并按策略恢复或终结；合法树仍返回，不能记作语义不匹配。 |
| 23 | “西刘塬光伏场区（1.90216MWp）→安装部分→光伏组件→具体组件” | 第一层为 PROJECT，中间为 SUBSECTION，实物按企业规则分类；完整层级返回，1.90216 不变成工程量。 |
| 24 | 没有真实来源工程标题的料表 | 不自动补工程根；普通章节不因名称或位置自动升级为 PROJECT。 |

补充核验“每 100 套”、数量父项缺量、属性尚未确定归属、单行并列实物尚未可靠拆分，以及单位需要换算但没有已配置依据的情况。所有原文必须可追溯，无法确定时进入相应待确认状态。

逐项对照企业专家答案，分别记录行覆盖、实物完整性、父子关系正确率、设备材料分类正确率、首轮候选召回率、最终 CBS 正确挂接率、错误自动挂接数、错误自动确定数量和人工确认比例。样例数量和业务范围须随报告给出，不能用 JSON 合法率代替业务质量。

## 9 验证精简架构、批量和恢复

### 9.1 单文件运行与阶段检查点

| 场景 | 必须观察的行为 |
|---|---|
| 正常完整文件 | 一次 Dify 运行依次执行三个模型；三个 Schema 各自正确；最终结果由服务持久化并可完整读取。 |
| 只有结构化对象输出 | 采用三个标准序列化节点的 25 节点版；模型对象不被手工拼接或重复编码。 |
| claim 被重复调用或携带错误实际运行身份 | 原子拒绝重复占用、错文件或旧运行写入；不能在未登记运行下调模型。 |
| reader 收到 HTTP 200 但 status、身份、版本或 `entry_phase` 非法 | reader 报错；服务对账并保留具体原因，不继续模型或保存结果。 |
| 首轮结构需修复 | 保存非终态 `REPAIR_REQUIRED`；旧运行停止后服务主动发起新派发，复用结构模型，修复次数最多一次。 |
| 结构阶段已经保存但响应丢失 | 恢复从 `CBS_LEAF` 或服务决定的后续入口开始，不重复成功的结构模型。 |
| CBS 首轮已经保存但响应丢失 | 恢复从 `CBS_PARENT` 或直接返回开始，候选和上下文不变化，不重复成功首轮。 |
| 文件结果已保存但 finalize 或 End 回执丢失 | 对账回读原结果；返回同一不可变修订，不重建树、不覆盖成功结论。 |
| 返回入口是 RETURN，但文件仍待修复或恢复 | 正常 End 不把文件改成完成；服务继续推进持久状态。 |
| CBS 无候选、容量超限或技术失败 | 已有合法树均保存并返回；阶段原因和业务未匹配、技术失败分开记录。 |
| 结构容量超限且没有合法结构 | 不调用超容量模型、不截尾造树；文件为明确的无可用结果 `UNAVAILABLE`。 |
| 正常结束、异常终止及流断开 | 服务均核对运行和检查点；正常与异常两条终止路径都有闭环，不依赖 End 输出完整状态。 |
| 两个同名同父节点被首轮分别判 match/no_match | 不产生假唯一目标；返回完整树及未挂接，reasonCode=CBS_OUTPUT_INCONSISTENT；来源树 READY 时保持 READY。 |
| task_id 未取得、停止使用 run ID、停止 user 错误 | 不生成错误停止请求；身份未知继续查证，不能凭停止确认释放未知模型占用。 |
| 首轮后新版本发布，原文件进入纠正或恢复 | 仍调用原 workflow_id；不支持指定版本时仍路由原不可变应用。版本不可用或 claim 版本不符时不调用模型。 |

### 9.2 批量、幂等与多用户

1. 相同身份、幂等键和输入重复提交只生成同一任务；相同键改变输入返回冲突。
2. 同一批中一份文件失败，其他文件继续；服务按预期文件清单检查终态，不能漏掉没有 End 回执的文件。
3. 模型漏行、非法父节点、截断 JSON 与依赖错误分别处理。结构修复有上限，技术重试不重复已经持久化成功的模型阶段。
4. 结果保存前修改文件、CBS、规则、人工结果或批次状态，旧结果不能写入当前业务数据；删除文件后的迟到结果同样作废。
5. 断开流连接、终止 Dify 运行或重启调度器后，服务先核对实际运行和检查点。租约到期不能直接证明旧运行已停止，也不能立即释放槽位并重派造成重叠执行。
6. 分页返回按不可变结果修订收齐，拒绝混用游标和版本；重复导入不新增 UUID 记录、计量对象或固定分组。
7. 重建单个文件不影响其他文件。两个请求同时构建同一文件按既定占用冲突策略处理，幂等重传不生成新代次。
8. 多用户请求的租户、项目、文件任务、输入包、规则、CBS 快照及结果互不混用；查询与下载也校验权限。
9. 两份文件并发挂到同一 CBS 时各自来源树保留；固定分组通过唯一约束复用，不能清空整个 CBS 的记录。

首轮容量配置可从**全服务最多 4 个活跃单文件 Dify 运行**开始，由共享调度状态约束所有服务实例。每个运行内部模型阶段串行；不再采用“两个批量 dispatch × 每批迭代并发 2”的画布配置。

“4”只是本任务链的初始并发预算，不证明模型供应商真实总并发也是 4。其他应用、保留的旧 Workflow、插件重试和仍未停止的运行可能共享供应商配额，实施时统一核对并记录。不要为实现本方案而修改旧应用；共享限流和排队策略由服务及供方配置协调。

## 10 验证时延、记录证据并交付

1. 用相同样本集分别测试单文件、10 文件和实际批量，分开记录 Java 解析、排队、claim、三个模型、结构修复、服务组装、结果传输和 Java 保存耗时。
2. 记录真实运行数、模型调用数、输入输出 Token、技术重试、失败率、待确认比例及整批完成时间。正常三次模型与修复四次模型是路径基线，实际故障重试单列，不能隐藏费用或延迟。
3. 在业务质量不降低的前提下比较不同并发设置。22 个节点或 25 个节点本身不能证明速度或成本已改善，须以相同条件的实测数据说明。
4. 改变企业规则、提示词、模型、源文件、CBS 和人工确认版本，核对快照绑定、缓存失效及旧结果冲突处理。
5. 交付新应用配置、版本记录、完整接口样例、错误说明、验证脚本输出、已执行/未执行清单及真实业务验收结果。未提供的样例、未执行的模型验证和未完成的部署测试明确记录。
6. 核对旧应用节点、连线、提示词、环境变量和发布版本与基线一致；若复用了共享服务模块，验证旧入口仍兼容。Java 新调用使用新应用 Key。

发布按既有部署授权和项目流程执行。Java 正式调用采用新应用的公开 Workflow API；草稿运行、只返回 Dify End 身份或本地清单校验均不能代替已发布链路和完整结果接口验收。
