# Java 专用 Workflow 精简修订

修订日期：2026-10-27。当前内部方案版本：quantity-workflow-slim-v1.1。状态：待实施、未连接真实 Dify 或模型；本包提供文档、契约样例和逻辑清单，不是已部署应用。

## 本次审查修订

1. 首轮按 leaf_name.strip() 校验同名候选的 judgment 一致性，全部 ID 仍独立保留。冲突直接返回完整树和“未挂接”，不产生假唯一目标，不增加模型调用。
2. AI 服务保存 task_id、workflow_run_id、实际 user 及应用身份。停止使用 task_id，运行查询使用 workflow_run_id；停止确认不等于实际终止。
3. 首次执行、纠正及恢复绑定同一个 execution_config_id 和已发布 workflow_id。目标版本支持时指定版本运行，否则使用不可变 Java 应用版本。现有 HTTP 与 reader 增加版本校验，核心节点仍为 22 个。

按用户确认，CBS 未匹配、冲突或技术失败在页面统一归入现有“未挂接”，可使用“挂接”按钮处理。semanticStatus 只反映来源树的结构、分类、数量和解析质量；仅 CBS 未挂接不触发 REVIEW。三个模型输出 Schema 保持兼容，CBS 首轮 System 和程序校验增加同名一致性规则。

## 结论

原方案不必保持57个节点。本版删去重复的画布包装，保留22个核心节点；若模型插件没有完整text而只有structured_output，则为需要适配的模型按需增加安全序列化Code，最多3个、合计最多25个。节点数量属于配置设计，不是已验证的运行指标。

核心职责仍是：理解结构和分类、必要时纠正一次、按单位工程名称及直接父节点名称做两轮CBS判断。JSON/身份/来源/数量/版本校验、CBS失败保留合法树、异步隔离和幂等仍全部要求实现。

## 主要改变

| 原设计 | 精简设计 |
|---|---|
| 一个Dify运行处理最多4文件，另有迭代和批次回执 | 一次运行只处理一份文件，AI服务公平调度整批 |
| 首轮与纠正各一套模型、提交、读取、接受链 | 同一结构模型及提交链；服务记一次纠正，新dispatch从纠正阶段继续 |
| 多个只传结果引用的Accept/Final/Envelope/Aggregator节点 | 后续阶段从服务回读已保存快照，End只返回入口身份 |
| 画布分别保存结构失败、CBS失败、派发失败并对账 | AI服务对所有正常/异常结束统一核对持久状态及有界恢复 |
| 单独finalize HTTP及包装 | CBS准备/校验和恢复器复用同一幂等发布函数 |
| 三个模型输出先包装成请求JSON | 完整text直接作为raw body提交；仅对象输出时保留必要序列化 |

## 不能删除的内容

- 三类语义模型及各自Schema；设备/主材仍按企业规则。
- 结构校验与一次纠正能力；不因移除独立sLLM2节点就取消纠正。
- CBS首轮保留候选、第二轮用相同原文并比较直接父名，最终挂单位工程。
- 服务端来源追溯、数量复算、当前派发及版本校验。
- CBS不匹配或技术失败时保留完整合法来源树。
- Java按文件短事务保存，以及多用户隔离、全局限流、旧结果防覆盖。

## 代价与边界

正常文件通常仍为1次Dify运行、3次模型调用。结构纠正会增加1次Dify运行，并增加1次语义模型调用；技术重试另计。新增运行开销需实测，不能宣称精简节点就一定提速或减少模型Token。

AI服务必须交付持久阶段、运行追踪、正常/异常统一对账和公共发布函数。它们原本已被要求实现，本次集中职责并写清执行入口；不能只删画布节点而不承接这些功能。

全局并发改为最多4个单文件运行的实验初值，不再使用原“每批4份、全局2批、批内并发2”。共享模型凭据与未知远端请求仍计入供应方预算。没有压测证明任何数值最优。
