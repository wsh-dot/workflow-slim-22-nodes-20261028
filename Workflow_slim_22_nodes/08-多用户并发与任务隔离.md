# 多用户并发、任务隔离与阶段恢复

本文是待实施要求。新 Java 专用 Workflow 保留单文件的结构判断与 CBS 两轮主干，采用 22 个核心节点；仅有对象输出而无完整文本的 LLM 按需增加序列化节点，三个均需要时共 25 个节点。旧 Workflow 保持原样。共享调度、阶段存储、运行监控和 Java 后台导入均须交付服务实现，节点减少不表示这些能力已经具备，也不代表已完成并发压测。

## 1 异步受理与 Java 后台取回

对外继续使用 `POST /smartCost/ai/quantity/build`、任务查询及文件结果接口。一个 job 可以包含多份文件；每个 dispatch 只绑定一个 file job 和一个实际 Dify run。正常文件在一个 run 内完成结构、CBS 第一轮和第二轮；文件之间由 AI 服务调度。

Java 从登录上下文确定租户、提交者和项目权限。提交时用短事务保存构建意图、不可变请求快照、构建代次及文件占用，并登记待发送任务。AI 服务在同一事务保存幂等记录、job、file job 和待调度记录，持久化成功后才返回 HTTP 202。

Java 后台发送与对账不依赖页面。响应丢失时，使用原 requestId 和原快照重传幂等 POST，取得原 jobId；不能重新生成代次，也不能先释放文件占用。明确未受理的错误才按状态机撤销或继续等待，不能单凭超时认定未受理。

Java 主动后台查询文件状态，取得同一 resultRevision 的完整 tree、cbsMatch、rowDispositions 和 issues 后保存。页面关闭、Java 实例重启或一次拉取失败后，持久待办继续处理。分页未齐时不提交；本地应用记录与业务写入同事务提交，重复拉取不重复入库。

队列容量不足时可在受理前返回 429 和 Retry-After；原幂等请求的重传先查已有受理记录，不因队列满而拒绝回读。队列容量、单次请求文件数及输入大小的上限须在部署配置中明确。

## 2 单文件运行与实际模型预算

| 配置 | 待测初值或约束 | 控制位置 |
|---|---|---|
| 每个 dispatch | 恰好一个 file job、一个 Dify run | AI 服务任务与运行记录 |
| 活跃单文件 run | 全服务合计最多 4 个 | 共享调度槽与原子领取 |
| 同一 file job | 同时最多一个有效执行租约 | 文件任务状态与 fencing |
| 单文件模型阶段 | 串行执行；正常最多三次，结构纠正最多另一次 | 服务阶段状态与 Dify 动作分支 |
| 实际模型并发、RPM、TPM | 按模型凭据和部署额度独立配置 | 共享模型网关 |
| 用户份额与队列容量 | 按负载和公平目标配置 | 入口与共享调度器 |

原来的“每批 4 份、全局 2 批、批内并发 2”不再作为执行配置。新画布没有多文件 Iteration。4 个单文件 run 是起点，不是已验证的最优值；模型阶段串行时，本任务链正常最多产生 4 个同时活跃的模型调用。

多个 AI 服务实例共享这 4 个槽，不能各自使用并发 4 的进程内信号量。运行领取、owner、租约、dispatch 归属和槽位变更使用共享状态及原子条件更新。

运行槽占用不等于模型正在执行，也不等于已经产生模型计费。旧 Workflow 或其他应用共用模型凭据时，网关须把它们与新应用一起计入实际模型并发、RPM 和 TPM。关闭画布的模型自动重试，仍需核对供应商插件的重试行为。

远端是否停止尚不明确的调用继续占用对应预算。Dify 节点超时、流连接中断或租约 TTL 到期都不能证明模型已经结束，不能据此立即释放容量并启动替代调用。

## 3 身份与授权范围

| 身份 | 约束 |
|---|---|
| tenantId、actorId、项目范围 | Java 从可信身份与权限生成；AI 服务仅接受已认证 Java 服务传入的上下文 |
| clientAppId、requestId | clientAppId 来自服务认证；requestId 标识一次构建意图 |
| jobId、file_job_id | 绑定受理请求、文件及不可变快照 |
| dispatch_id、workflow_run_id | 前者是服务派发身份，后者是 Dify 实际运行身份，不能互相代用 |
| task_id、dify_user | 从实际 streaming 调用记录取得；停止任务使用 task_id 及原 user，不使用 workflow_run_id 代替 |
| execution_config_id、workflow_id、observed_workflow_id | 冻结执行配置、预期发布版本及实际版本；同一文件的首轮、纠正和恢复均核对一致 |
| fileId、fileRevision、buildGeneration | Java 文件、输入修订与构建代次 |
| packet_id、context_id | 结构输入包及固定 CBS 证据；引用须属于当前文件与快照 |
| stage、attempt_id、fencing token | 服务分配的阶段、执行尝试与当前写入资格 |
| resultRevision | 本代次发布的不可变文件结果版本 |

Java 与 AI 服务之间使用服务认证，查询进度和结果仍检查租户、项目及授权范围。共享项目成员的访问按项目权限判断，不默认仅提交者可读，也不默认所有用户可读；知道 UUID 不构成授权。

Dify 使用新应用的独立 API Key。调用 user 由可信租户与提交者生成稳定的非敏感标识，并保存实际使用值；它用于运行追踪，不能替代业务权限检查。Dify 内部 HTTP 使用独立服务凭据，携带当前 dispatch 和已领取的执行身份。

输入、阶段结果和文件结果按 tenant/job/file_job/版本隔离。文件名仅展示，不作为唯一存储键；共享环境变量只存配置和密钥，不存当前用户输入、候选或模型结果。

## 4 启动领取与阶段入口

AI 服务先持久化派发意图、entry_phase、当前 attempt、execution_config_id 和槽位占用，再按 02 §7.4 的固定版本方式调用 Dify，response_mode=streaming。第一个内部请求必须是 `POST /internal/quantity/dispatches/{dispatch_id}/claim`，携带真实 workflow_run_id、实际 workflow_id 和冻结配置标识。任何模型节点执行前都必须成功领取。版本或配置不符返回 409 EXECUTION_VERSION_MISMATCH，不向该运行提供输入。

claim 原子核对当前文件租约、dispatch 有效性和运行绑定：同一 dispatch 与同一 run 的原样重传返回原领取结果；不同 run 竞争同一 dispatch 被拒绝。fencing 版本保存在服务内部；后续读取与提交依据 dispatch_id + 实际 workflow_run_id 回读该版本，并原子校验当前归属和写入资格，不要求画布另传 token。旧派发不得读取新阶段输入或提交迟到结果。

实际 Dify 部署是否提供可绑定的 `sys.workflow_run_id` 必须先验证。不能把 dispatch_id 填作 run ID，也不能凭空引用系统变量。该能力未验证时，不启用自动重派；须先提供可核对的运行登记替代方案，否则转人工查证。

服务把 claim 绑定的 run ID 持久保存。启动响应丢失时先检查该绑定和持久阶段；尚无绑定的派发进入运行待查证状态，不因 TTL 自动重启。租约接管只赋予查询与对账责任，不等于获准再次调用模型。

AI 服务从实际 SSE 事件保存 task_id，并将其与当前调用、workflow_run_id、dify_user 及应用凭据引用绑定。claim 先到时允许 task_id 暂空，后续按运行身份补齐；多个重复运行分别记录，不能覆盖获准执行者。取消使用 `/workflows/tasks/{task_id}/stop` 和原 user，查询使用 workflow_run_id。未取得 task_id 时进入运行查证，不伪造停止身份。停止确认不等同于运行结束；未知远端模型占用继续计入预算。准确请求与查证条件统一见[接口契约 7.4](02-接口与节点契约.md#74-dify-调用运行身份与固定版本)。

同一构建代次的纠正及技术恢复始终使用原 execution_config_id。支持指定已发布版本时调用 `/workflows/{workflow_id}/run`；不支持时使用 IMMUTABLE_APP 隔离应用版本，并冻结其发布配置、环境变量和模型配置，直至原任务及待恢复任务处理完毕。目标版本不可用时记录 EXECUTION_VERSION_UNAVAILABLE，不改用新版本。该条件由服务有界恢复策略处理：已有合法树则保树返回未挂接，semanticStatus 沿用来源树质量，没有合法树则明确失败，不无限等待，也不丢弃旧阶段记录。

AI 服务是阶段状态的唯一决定源。entry_phase 来自持久记录，画布按动作进入对应阶段，不根据模型文本或临时变量猜测恢复位置。

| entry_phase | 可执行内容与必要前置 |
|---|---|
| STRUCTURE_INITIAL | 首轮结构阶段尚未成功；读取服务固定的完整输入 |
| STRUCTURE_REPAIR | 已保存首轮提案与校验错误，且一次纠正预算尚未使用；复用同一个结构 LLM |
| CBS_LEAF | 已有合法结构；读取固定证据与完整单位工程候选 |
| CBS_PARENT | 已有合法结构及成功首轮候选；直接读取服务保存的第二轮输入 |
| RETURN | 本次运行无需继续调用模型；是否文件终态仍由服务持久状态决定 |

每个阶段准备接口从持久快照读取输入和引用。恢复第二轮时不依赖本次 run 中未执行的结构或首轮节点变量，不重跑已成功模型。无合法候选或容量超限等动作由服务生成，并保留已有合法结构。

## 5 结构纠正、技术重试与检查点

结构首轮需要纠正时，服务原子保存首轮提案、错误和待纠正状态，画布结束本次 run。监控确认该 run 终止后，服务以新 dispatch 的 STRUCTURE_REPAIR 入口复用结构 LLM。纠正输入包含完整原输入、首轮提案及明确错误。

每个文件构建代次最多一次语义结构纠正。该预算不随 dispatch 或 run 重置；第二次结构校验只能通过或明确失败。技术错误不消耗额外的语义纠正次数，但每次技术执行都受独立的次数与总时限预算约束。

HTTP 传输重试使用同一 attempt_id、同一原始模型文本和同一请求体；相同键同内容返回已有结果，不同内容返回冲突。不得重新调用模型生成一份新答案后冒充原请求重传。新的技术尝试由服务分配独立 attempt_id，且只针对尚未成功的阶段。

结构、CBS 首轮和 CBS 第二轮提交接口都必须持久化阶段检查点。阶段结果、下一动作及待继续或待发布记录在同一事务内提交；重启后的恢复任务能扫描这些待办。不能只在 HTTP 响应里返回下一步而不保存。

如果阶段已经保存而响应丢失，恢复任务回读该检查点继续，不重复消耗结构纠正预算，不重复执行已成功的 CBS 第一轮。所有提交校验文件身份、快照、当前 attempt，以及由 dispatch_id + 实际 workflow_run_id 关联的服务内部 fencing 版本，不能只检查 attempt 字符串。

## 6 统一运行对账与结果发布

正常 End 只返回 dispatch_id 和 file_job_id，用于关联当前调用。它不是文件成功回执，也不携带完整树。服务校验身份后回读持久阶段和结果；不能把 Dify 正常结束、空输出或 HTTP 200 等同于文件成功。

所有技术异常使当前 run 失败，由外部运行监控统一处理。监控同时覆盖正常结束、异常结束、结束响应丢失和画布未到 End 的情况，依据持久状态决定发布、继续缺失阶段或进入运行待查证状态。不能只靠成功回调触发对账。

CBS 第二轮完成、首轮无候选或明确容量问题时，服务在合法结构基础上生成文件结果。阶段已成功但最终发布事务失败时，持久发布待办继续重试，保留原阶段结果，不再调用模型。

CBS 技术恢复预算耗尽且已有合法结构时，发布完整树及未挂接结果，文件 semanticStatus 沿用来源树质量，cbsMatch.executionStatus 为 FAILED，保留失败原因。不能用“语义不匹配”代替技术失败。没有合法结构且恢复耗尽时，文件执行失败，不生成半棵树冒充结果。

成功提交与失败收口使用同一阶段状态及版本条件进行原子比较更新。既有成功阶段不能被迟到失败覆盖；失败先到、原成功请求后到的反向时序也必须受当前 attempt 和发布状态约束。不能仅凭当前 dispatch 相同就允许写入。

每个 file job/buildGeneration 只发布一次不可变文件结果；终态后迟到成功或失败均不改写它。若需改变已发布结果，Java 发起新的 requestId 和 buildGeneration。可复用版本完全一致且适用的合法结构，但须校验文件、CBS、规则与人工修订基线，不复用过期证据。

任务统计以各文件持久终态为准。结构可用但 CBS 失败的文件单列 CBS 技术失败及未挂接数量，不冒充全部挂接成功。待恢复文件保持处理中，并显示恢复原因；不要提前把整批计为完成。

## 7 幂等、同文件互斥与 Java 入库

受理幂等范围为 tenantId、已认证 clientAppId 和 requestId，规范化输入摘要包括可信 actorId、项目、文件修订、CBS 与规则版本、输入和构建代次。共享数据库唯一约束解决并发先查后建；同键异输入或身份返回 409。

不同 requestId 同时构建同一文件时，Java 返回 FILE_BUILD_IN_PROGRESS 及有权限查看的冲突信息。批量请求含冲突文件时在受理前返回冲突清单，不悄悄跳过后声称全批受理。正常新意图在前次结束后递增 buildGeneration；明确取代在途任务时须使旧代次失效，并对旧运行执行取消与对账。

文件占用、构建意图和受理状态持久关联。Java 或 AI 服务重启后按记录恢复发送、查询、导入和释放占用，不能根据等待时间直接清除。模型运行期间不持有业务数据库长事务或行锁。

Java 保存采用文件级短事务，检查文件仍存在、项目和批次允许导入、fileRevision/buildGeneration/CBS/规则版本有效、人工修订未变，并以 jobId + fileId + resultRevision 的唯一应用记录防止重复导入。

Java 为来源节点生成正式 UUID，保存 resultKey 映射、父子关系、同级顺序、类型、数量口径和来源。按文件替换来源树，不删除同 CBS 下其他文件的记录；共享固定分组以项目、CBS 节点和分组类型唯一约束复用。检查与写入在同一事务或等效并发控制中完成。

AI 处理成功和 Java 接受入库是两个状态。Java 后台记录待拉取、待应用、已应用、版本冲突或应用失败，并据此向页面展示。文件删除、批次锁定或人工修订造成的过期结果不得覆盖业务记录，也不得显示为已挂接完成。

## 8 公平调度与必要验收

可从 actor 轮询与可配置的活跃份额开始；无人等待时允许借用空闲容量，新用户到来后在当前运行结束时重新分配。用户份额不是固定最优值 2。租户与用户的配额关系须明确，不能把按用户公平自动等同于按租户公平。

大文件和长尾调用仍可能长期占用单文件槽。压测须包括大小文件混合、大批量与单文件竞争、多租户多 actor、实例扩容及模型限流，记录实际等待和完成分布后调整运行数和份额，不只比较平均耗时。

实施后至少验证：

1. 多用户同名文件互不混用；跨租户、跨项目、篡改 actor、跨 file job 和跨 dispatch 的读取或提交被拒绝。
2. 同 requestId 并发提交只创建一个 job；同键异体返回冲突；不同请求争用同文件被拦截。
3. Java 占用后未发送、AI 受理响应丢失及 Java 重启后，原请求能继续对账，文件不永久悬占。
4. Dify 已启动但调用方未取得 run ID，claim 与启动响应分别丢失时，能查证真实运行，不盲目重派或释放预算。
5. 首轮结构要求纠正后结束 run；新 run 从 STRUCTURE_REPAIR 进入，复用模型节点且总纠正次数不超过一次。
6. 已保存结构或 CBS 首轮后 run 失败，新派发直接进入缺失阶段，不重跑成功阶段；不同 run 竞争同一 dispatch 被拒绝。
7. 阶段提交成功但响应丢失、发布事务失败及服务重启后，持久待办能发布同一结果，不重复执行模型。
8. 成功先到/失败后到和失败先到/成功后到均不能覆盖已发布结果；CBS 恢复耗尽仍返回合法完整树及技术失败状态。
9. 多实例合计运行数遵守共享上限；旧应用共用凭据、远端超时未停止及限流时，实际模型预算仍可核对。
10. 两文件并发写同 CBS 均保留，固定分组不重复；旧代次、人工修改、删除文件和锁定批次的结果不能错误入库。
11. 关闭页面并重启 Java 后后台仍取回结果；分页不混版本、重复轮询不重复生成 UUID，AI 完成与 Java 应用状态一致可查。
12. End 仅含身份、正常结束后尚有恢复动作、异常结束未到 End 三种情况，监控都以持久状态对账，不误报成功。

压测记录样本规模、到达速率、用户/租户分布、文件行数与候选规模、Token、排队及端到端 p50/p95/p99、实际模型并发、RPM/TPM、错误与重试、恢复时间和 Java 应用冲突。预先约定通过阈值；4 个单文件 run 与公平份额只在准确性、隔离和恢复要求均满足后再据测量调整。
